# 流水 · 决策记录

记已经定下来的事和定它的理由。后面推翻某条时，先看这里的理由还成不成立。

---

## D1 · v1 先做单 skill，不做全链路

**定了**：v1 交付出去应该长得像个点工具。全链路是叙事和终局，不是 v1 的形态。

**为什么**：调研说「没有覆盖全链路的产品，多数做 1～2 个单点」——这不完全是市场空白，也是因为全链路把意图识别变成了承重墙。所有难点（信息不足就规划、推荐不存在的工具、多意图、黑话）全是同一个组件的失效形式。

真正该问的不是「怎么把意图识别做准」，而是**「能不能让它少承重」**。

参照 Simplify：它一期根本没有意图识别。你在哪个网申页面上，页面本身就是意图。tracker 是自动填表的数据残渣长出来的，不是设计出来的。

---

## D2 · 痛点 chip 是主路径，自由输入是兜底

**定了**：首页把「求职—网申填表」「留学—文书微调投不同项目」这类痛点 chip 作为主入口，点击直接带参数进 run 页，**完全绕过意图识别**。自由输入框退成兜底。

**为什么**：chip 是一次**预声明的意图**——已知 skill、已知入参、已知产出。绕过识别不是妥协，是把承重墙拆掉。

现在原型是反的：`SAMPLE_INTENTS` 只是输入框的轮播 placeholder，点进去还是走 `routeIntent`。

**附带好处**：chip 可以直接用黑话写（「双非想冲港三」「大小周能不能接」）。既证明听得懂学生话，又根本不需要识别黑话。

---

## D3 · 意图识别约束成「排序 + 枚举」，不做自由生成

**定了**：永远不让模型说出工具名，只让它对检索出的候选做排序，输出固定枚举。

**为什么**：「推荐了不存在的工具」不是 prompt 问题，是 harness 结构问题。约束生成空间，一次性永久解决，不需要反复调 prompt。

现有 `routeIntent` 已经是在 `TOOLS` 上打分——换成 LLM 时守住这个形状就行。

**推论**：约束之后这个任务对模型能力几乎不敏感，所以用最便宜那档就够。

---

## D4 · 意图类型必须有 `unclear` 档

**定了**：`IntentType` 加 `unclear`，配反问 UI。反问必须免费、必须是一等产出。

**为什么**：现在 `IntentType` 只有 `simple | multi | longterm`，**数据模型压根表达不了「我不确定」**。配合 `detectScene` 在零命中时静默返回 `'study'`，和兜底的「按场景热度推荐」——任何一句看不懂的话都会被自信地推成学习提效热门工具。

不确定性要在数据模型里有位置，否则模型只会编。这跟 D7 里 `unknown` 档是同一个道理。

反问免费是必要条件：否则模型永远倾向于「先产出点什么」。

---

## D5 · 第一个 skill = 简历 × JD 匹配诊断

**定了**：不是文书微调（这是对上一版判断的修正）。

**为什么改**：读到 WhatAJob 之后发现两端入参**都已经有了**——

- 一个跑得通的规则简历解析器（pypdf layout 模式，双栏能还原）
- `jobs.db` 里腾讯/字节/百度/网易官网抓的**真实 JD**，带任职要求字段

重复结构和文书微调完全一样（一份文档 × N 个目标，重复性内生，不需要浏览器插件），但造得起、测得起。产出是打分卡，eval 最便宜。

**取舍**：简历诊断赛道比文书微调挤。但现在选的是**测试载体**，不是对外产品主张——第一个 skill 的任务是验证 harness 和 artifact schema 立不立得住，「能不能便宜地造出来并测出来」压倒一切。楔子对外怎么讲，等 harness 验完再定（见 待定事项）。

**另外**：现有「全库匹配」是个推荐器（简历→排序岗位），比诊断器更"完成"，但难 eval——「最佳岗位」没有 ground truth。留着当第二个 skill。

---

## D6 · artifact 必须带类型，一期就定

**定了**：每步往工作台写**命名带类型**的对象，每个 skill 声明它消费哪些**类型**。第一个 skill 的产出叫 `match.report`，不叫 `resume`。

**为什么**：「简历修改→模拟面试，把上一环的结论误当成简历本身」这类失真，病根是**步骤之间传的是散文**。「调用前把工作台上下文拼进 prompt」还是散文塞散文，失真会换个形式回来。

下游面试 skill 声明消费 `resume`，那么一份 `match.report` 在**结构上就不可能**被喂进去。靠类型挡掉，不靠 prompt 里叮嘱。

**为什么一期就定**：schema 后补极贵。先按拼 prompt 的路走一版，会把失真固化成「既有行为」。

## D7 · 规则分照算，但不进 prompt，只写 `meta.ruleScore`

这条之前没讲清楚，展开写。

### 设定

你有**两个判官**在看同一份简历和同一条 JD：

- **判官甲（规则）**：`whatajob-match-v3`，三维加权算出一个分数
- **判官乙（模型）**：读原文，逐条判定 matched / gap / unknown

问题是：要不要把甲的分数写进乙的 prompt？

### 一个具体例子

简历是个产品实习生，里面写着：

> 负责推荐策略迭代，与算法同学对接 AB 实验
> **独立实现 DIN 模型并上线，CTR +3.2%**

JD 要求「熟悉主流推荐算法（协同过滤、DSSM、DIN 等），有大规模推荐系统落地经验」。

规则层怎么算：技能维度命中「推荐」，但 `classify_family` 把简历判为「产品」族、岗位判为「技术」族，族不一致触发 `_FAMILY_PENALTY_MISMATCH = 0.35` → **总分 41**。

规则**漏了**第二行——`DIN` 不在 `_SKILL_KEYWORDS` 词典里。

### 情况 A：把 41 分喂进 prompt

prompt 里写着「规则打分 41/100（偏低）」。

模型看到 41，**倾向于输出 mismatch**。它可能碰巧对，但这次它错了——那行 DIN 才是决定性证据，模型本来读得懂，却顺着低分把它忽略了。

更糟的是：**你永远分不清模型说 mismatch 是因为它读懂了，还是因为你告诉它分低。** 判官乙戴上了判官甲的帽子。你花了两份钱，只买到一个判断。

### 情况 B：不喂，只存 meta

模型独立读，看到 DIN 那行，输出 `fit`。

于是：**规则 41 vs 模型 fit = 分歧**。这条自动进复核队列。你一看就明白了——`DIN` 该加进技能词典。

**规则层因此变好了，而且是靠模型免费发现的。**

### 这条决定的真正价值

**分歧是资产。**

两个判官独立，分歧率就是一个**免费的质量指标**；而每一个分歧都是一条**已经标注好的样本**，直接告诉你该修词典还是该修 prompt。

你现在没有 eval 标注，人工标注很贵。分歧给你一个**按优先级排好的复核队列**——只看两边不一致的那 10%，不用看全部 100%。

把分数喂进去，分歧率会人为降低。看起来一致了，但那是**假的一致**，你什么都学不到。

> 类比：双盲读片。两个医生独立看同一张片子，不一致的才值得会诊。如果第二个医生先看了第一个的结论，一致率必然上升——但那不是更准，是更盲。

### 什么时候可以喂

要分清两件事：

| 喂什么 | 现在能不能 |
|---|---|
| 喂**答案**（「规则算了 41 分」） | ❌ 不行，毁掉独立信号 |
| 喂**去哪里看**（检索提示，如「这几段可能相关」） | ✅ 可以，不构成答案泄露 |
| 用规则**预筛候选**（决定调不调模型，省钱） | ✅ 可以，那是「看不看」不是「答案是什么」 |

以后你已经信任模型、规则退成预筛时，第三种是正常做法。但内测期诊断价值远大于那点成本，先保持双盲。

## D8 · 模型：先只接一家，百炼 Qwen-Plus

**定了**：只接阿里云百炼 Qwen-Plus。诊断 skill 和意图路由先都用它跑通。

**为什么只一家**：现在 0 个 skill、后端还没写。两家 = 两套 SDK、两套鉴权、两种失败模式、两种 JSON 遵循习惯。等**测出**某任务确实需要另一档再加。

**为什么是百炼而不是 Claude**：不只是便宜。这是国内部署的学生产品，Anthropic API 在大陆没有直接接入，从境内服务器调会同时带来延迟、付款、**数据出境**三个问题。而这个 skill 处理简历——个人信息，跨境传输在《个人信息保护法》下是要走合规流程的实项。境内托管 + 人民币结算 + 无出境问题，这是硬理由。

**为什么诊断 skill 不需要更强的模型**：它是「对着给定文本逐条分类 + 抽原文引用 + 填固定 schema」——分类和抽取，不是开放生成。更贵的档位在这类任务上换不来可测出的质量差异。

**留缝**：
- 走百炼的 **OpenAI 兼容接口**，不用原生 SDK → 以后换供应商基本零成本
- **schema 校验 + 失败重试放 harness 层，不写在 prompt 里** → 换模型时不用重写所有 prompt

**降档留到有量之后**：意图路由理论上可以用比 Qwen-Plus 更便宜的档（它是每条 query 都调的地方），但先都用 Qwen-Plus 跑通，等有真实调用量再按数据降。

## D9 · qa_skill 兜底必须埋点

**定了**：做 qa_skill 兜底（mt 的建议），但每次落到它都要记录，并定一个兜底率阈值，越线当 bug 处理。

**为什么**：每次落 qa_skill 都是一个信号——要么缺 skill，要么识别漏了。**qa_skill 的日志就是 skill roadmap**，这是内测前最值钱的那份数据。

**反面风险**：qa_skill 很容易变成一个舒服的垃圾桶，把低覆盖率盖住。所以只优雅降级而不记录是不行的。

---

## D10 · eval 语料从真实捞种子，不从 AI 生成

**定了**：先从真实语料捞种子（小红书/牛客/一亩三分地提问帖、能拿到的群聊），再用 AI **扰动**，而不是从零生成。

**为什么**：LLM 生成的 query 来自它觉得自然的分布，**恰好系统性地缺最该测的那几类**——真黑话、懒到只有六个字、错别字、中英混杂。真实学生 query 比任何 LLM 自发生成的都更短、更脏、更懒。

**另外**：现在就该建固定 eval 集并版本化，否则调 prompt 没有回归信号，修一个坏一个。

`routeIntent` 现在是纯确定性函数，**不接模型就能跑出 baseline**。已知它一定会挂的一条：`q.length > 34` 被当作多步骤信号，任何说得稍详细的单一目标都会被误判成多步。

## D11 · 必须显式关掉思维链

**定了**：调模型一律带关思维链参数（`llm.py` 的 `_NO_THINK`）。要开得显式 `LLM_THINKING=1`。

**为什么**：这是**产品可行性问题，不是优化问题**。同模型 `deepseek-v4-pro`、同 6 条 case 实测：

| | 耗时 | out token |
|---|---|---|
| 思维链开 | 63.6–135.9s（中位 100s） | 32701 |
| 思维链关 | **5.8–6.7s** | **2184** |

14–20 倍加速，token 降 15 倍，三条不变量两边都 6/6 通过。用户在首页点一下等 100 秒，产品就死在这。

这个 skill 是**逐条分类 + 抽原文引用**，不是推理题。思维链在这里没有产出，纯烧时间和 token。

**意外收获：关掉之后判定质量反而变好。** `unknown` 从 15/25 降到 8/25。开思维链时模型越想越犹豫、往 `unknown` 躲。

**坑（写进 `llm.py` 注释了）**：开关名各家不统一，且**不认识的参数会被静默忽略、照样返回 200**。所以加新供应商必须实测 out token 有没有真降，不能看有没有报错。`glm-5.3-flash` 是反例：没有任何开关能关掉它的思维链，能压低 token 的那两个直接把 JSON 弄坏了——**只看 token 下降会把破输出当成优化**。

## D12 · `unknown` 的判据是「有没有本该写的位置」，不是「难不难判」

**定了**：判 `unknown` 之前先问：简历里有没有一个**本该列出这项的位置**？有而没列 → `gap`。没有这个位置 → `unknown`。

**为什么**：人工核了 6 条 case 的 8 条 `unknown`，**3 条判对、5 条偷懒**。偷懒的有共同模式——简历有「技能特长」小节写着 `SQL、Excel、Axure、Figma`，JD 要求「熟练掌握至少一种编程语言」，模型判 `unknown`。

**一个人把技能列全了而编程语言不在里面，这是「缺失的证据」，不是「证据的缺失」。** 模型把这两件事当成一回事了。

D4 定了「`unknown` 档位必须存在」，但只说了要有，没说什么时候用。不给判据，它就会退化成逃避档位——什么都判 `unknown`，看起来很谨慎，实际没有信息量。

**同时揪出一类比偷懒更危险的错判**：要求「积极乐观,认真负责,乐于协作」判 `matched`，引用「与算法团队对接需求」。职责描述推不出性格。这是**安慰话套了个 evidence 的壳**——引用本身逐字没错，推论是编的。

**关键**：三条机械不变量对这类错判是**盲的**，因为那句话确实逐字出现在简历里。所以质量断言（`eval.jsonl` 的 `statusIs` 那套）不是不变量的补充，是**另一层不同性质的闸门**，不能只靠不变量。

据此 `prompt.md` 从 7 条硬规则扩到 9 条，新增：
- 规则 6：软素质要求不许拿职责描述当证据，宁可 `unknown`
- 规则 7：区分「没写」和「写全了但不包含」
- 规则 8：一条要求混了硬门槛和加分项时，按硬门槛判

**规则 8 是被自己的修复逼出来的**：改完前两条后出现新错判——「本科及以上学历在读,计算机相关专业优先」判成 `gap`/`blocking`。本科在读是满足的，「计算机相关专业优先」只是加分项，判 `blocking` 等于把够格的人直接筛掉。收紧规则会产生新的越界方向，每轮都要重新核。
